# L2Train

Распределённая система управления несколькими игровыми окнами Lineage 2 на нескольких компьютерах: мультибокс-панель с автоматизацией. Один оператор управляет несколькими группами персонажей с разных машин из одного дашборда. Рутинные действия (бафы, хил, ресы, сбор группы, фарм) выполняются по командам или автоматически по тому, что система «видит» на экране.

Проект прошёл две итерации:
- **рабочая версия «Рифт»** — отдельные серверы на каждую группу, Telegram-бот, затем Electron-дашборд;
- **этот репозиторий** — переработка в универсальную платформу: оркестратор, клиенты на машинах, агенты сценариев и общий дашборд.

Подробный справочник по файлам и событиям находится в [ARCHITECTURE.md](./ARCHITECTURE.md), а ТЗ следующей версии с выводами по текущей — в [TZ_UNIVERSAL.md](./TZ_UNIVERSAL.md).

```
l2train/
├── backend/      NestJS-монорепо: apps/backend (оркестратор :2482), apps/machines (хаб машин), apps/launcher (связь с агентами)
├── client/       NestJS-приложение на каждой игровой машине: ввод (Arduino), окна (AHK), захват экрана, компьютерное зрение
│   └── python-vision-service/   Python-сервис: OCR (PaddleOCR), вырезание областей и сравнение с образцами
├── agents/
│   ├── rift-agent/   полная логика сценария «Рифт» (фасады классов, очередь действий, баф/рес/хил)
│   └── trade-bot/    трейд-бот: распознавание окна торговли через OCR
└── dashboard/    Nuxt 4 + Electron: управление группами, машинами и скиллами
```


Роли разделены так:
- **Оркестратор** знает, *что* нужно сделать: состав групп, какая машина за какой группой закреплена, какие команды доступны.
- **Клиент** знает, *как* физически это сделать на конкретной машине: нажать клавишу, переключить окно, посмотреть на экран.
- **Агент** содержит сложную автономную логику сценария. Она вынесена отдельно, чтобы не переписывать проверенный в работе код фарма.

## Ключевые механизмы

### 1. Шина событий с декораторами
Модули оркестратора не вызывают друг друга напрямую, а общаются событиями `@nestjs/event-emitter`. Поверх этого написаны свои декораторы (`common/decorators/event.buss.decorator.ts`):

| Декоратор | Что делает |
|---|---|
| `@EmittEvent('name', 'key')` | вызов метода сам публикует событие; суффикс имени берётся из payload (`core::scenario:getConfig.rift`) |
| `@EmittAsync('name', 'key')` | публикует событие и **ждёт ответы** обработчиков (`emitAsync`), то есть получается запрос-ответ поверх шины |
| `@HandleEvent('name')` | подписка (`OnEvent`) плюс трассировка: если событие пришло без зарегистрированного эмита, пишется `log:event.error` |

Имена событий строятся по схеме `источник::получатель:действие`, например `ws::core:nuxt.command` или `scenario::machinesHub:machine.command`. По имени события сразу видно, кто кому пишет. Благодаря динамическому суффиксу новый сценарий подключается, просто подписавшись на `core::scenario:getConfig.<имя>`, без правок ядра.

### 2. Типизированное API скиллов из конфигов (кодогенерация)
Скиллы каждого класса описаны данными: клавиша или ячейка панели, откат, длительность, пауза после применения, тип (`buff`, `skill`, `macro`):

```ts
warCry:   { key: '1',  duration: 57 * sec, pauseAfter: 150, type: 'buff', desc: 'Боевой клич' },
noblesse: { panel: 6, key: 11, type: 'macro', desc: 'Нобл с ВЛа' },
```

`ApiGenerator` (`game-api/game-api.generator.ts`) по этим конфигам генерирует TypeScript-интерфейс и реализацию для каждого класса (`VLActions`/`VLActionsImpl`) и группирует методы по типам. В итоге сценарий вызывает `party.VL.buff.warCry()` с автодополнением и проверкой типов, а не строку `'1'`. Команда из UI с id вида `{role}_{group}_{skill}` разбирается и выполняется через тот же фасад.

### 3. Сценарии как плагины
Сценарий регистрируется в ядре через конфиг, который возвращает три вещи:
- `basePartyConfig` — состав групп;
- `machinesActivateConfig` — какие машины за сценарием закреплены;
- `facadeFactory` — фасады персонажей.

`CoreService` создаёт для сценария `ScenarioContext`: резервирует машины, держит состояние групп (`ready`, `farm`, `trade`, `error`, `idle`, счётчик ошибок) и маршрутизирует команды:
- `target: 'machine'` → на клиент машины (одиночное действие);
- `target: 'agent'` → агенту сценария (сложная команда: «начать фарм», «собрать группу и к рифту»).

Сейчас реализован «Рифт», «PvP» заготовлен.

### 4. Клиент на машине: единый протокол примитивов
`CommandHandler` принимает команды пяти видов:
- `keyboard`: `pressButton`, `keyDown`, `keyUp`;
- `mouse`: `move`, `click`, `doubleClick`, `shiftClick`;
- `macro`: около 25 игровых макросов, например `switchWindow`, `pressAtPanel`, `chatCommand`, `attackStay`, `dragElement`, `releaseAll`;
- `vision`: `checkBuff`, `checkDebuff`, `targetExist` и другие;
- `settings`: разрешение, масштаб, калибровка.

Из этих примитивов собирается любое поведение верхнего уровня, поэтому новый сценарий почти не требует менять клиент.

### 5. Ввод через Arduino
Клавиатура и мышь эмулируются микроконтроллером Arduino, подключённым по USB как HID-устройство. Клиент общается с ним по Serial (`serialport`, 9600 бод) текстовым протоколом:
- команда отправляется строкой (`PRESS_AT_PANEL:6:11`, `SET_RESOLUTION:1366:768`);
- ответ приходит строкой `ADRUINO_RESPONSE|{json}`;
- `sendAsync` превращает обмен в промис с таймаутом 5 с, поэтому запрос-ответ работает поверх асинхронного порта;
- есть `virtualMode` для отладки без устройства.

### 6. Компьютерное зрение без доступа к игре
Система не читает память процесса и не перехватывает сетевой трафик. Всё состояние она получает **со скриншотов**, как человек:
- **ХП группы** (`party-health.service.ts`) оценивается по пикселям полосок здоровья в известных координатах интерфейса. Сначала проверяется маркер, что слот вообще занят персонажем. Отдельно обрабатываются питомцы и главный персонаж. Код рассчитан на фиксированное разрешение 1366×768.
- **Бафы и дебафы** (`status-panel.service.ts`) находятся сравнением иконок с образцами (`capture/samples/{buffs,debuffs}`).
- **Сложные случаи** (окно торговли, текст) отправляются в отдельный **Python-сервис** (`python-vision-service`, HTTP на `127.0.0.1:7001`):
  - распознавание текста через PaddleOCR (есть и вариант с Tesseract, модели `rus`/`eng`);
  - вырезание области интереса (ROI);
  - сравнение с образцом (`match-template`).

  Node.js-клиент общается с ним через `PythonBridgeService`; автозапуск сервиса из клиента (`python-launcher.service.ts`) заготовлен, пока его нужно запускать отдельно. Тяжёлое зрение вынесено туда, где для него есть экосистема, без попыток повторить OpenCV на JS.
- На основе зрения работают **наблюдатели** (`watchers`): контроль здоровья в рифте, автоматический рес (`resurection-controller`), проверка выхода из рифта, поиск угла для фарма.

### 7. Управление окнами через AutoHotkey
На одной машине запущено несколько окон игры, а Arduino нажимает клавиши только в активное. Поэтому клиент перед командами переключает окна и **спрашивает у Windows, какое окно сейчас активно** (AHK-скрипты `is_active.ahk`, `activate.ahk`, `win_watcher.ahk`), а не полагается на запомненное состояние. Почему это важно: повторное переключение на уже активное окно в Windows его **сворачивает**, и следующая клавиша уходит в никуда. Это решение пришло из эксплуатации первой версии.

### 8. Дашборд
Nuxt 4 + Vue 3 + Pinia + Tailwind, упакован в Electron со своей рамкой окна. Связь с оркестратором идёт по socket.io, состояние приходит пушем: оркестратор сам рассылает изменения через `NuxtStateUpdate`. Страницы:
- **«Рифт»** — таблица групп: статус, команды сценария (старт/стоп фарма, сбор группы) и `SkillSelector` (класс → скилл → ▶);
- **«Машины»** — список машин и их подключений.

## Решения и выводы

| Решение | Почему | Что показала практика |
|---|---|---|
| Распределённая схема: оркестратор + клиенты | Окна разнесены по нескольким ПК, ими нужно управлять централизованно | Работает, но три процесса бэкенда и шина со строковыми событиями дают много связующего кода до первой работающей кнопки |
| Event-driven вместо прямых вызовов | Слабая связанность, сценарии подключаются как плагины | Без строгой типизации имён событий сложно отлаживать; отсюда трассировка в `@HandleEvent` |
| API скиллов через кодогенерацию | Типобезопасность и автодополнение в сценариях | Каждая новая кнопка требует правки кода и перегенерации. Следующая версия (ТЗ) переносит классы, скиллы и макросы в данные, редактируемые из UI |
| Сначала обобщить самый сложный сценарий («Рифт») | Он уже работал и давал готовые требования | Это затормозило универсальную версию. В ТЗ v2 сделан вывод начинать с простых сценариев, а «Рифт» оставить отдельным приложением |
| Зрение по пикселям + Python OCR | Не нужен доступ к процессу игры; быстро для полосок ХП, точно для текста | Привязка к разрешению и раскладке интерфейса; нужна калибровка (`alignInterface`) |

## Запуск

```bash
cd backend   && npm i && npm run dev     # оркестратор :2482
cd client    && npm i && npm run dev     # на каждой игровой машине (.env: имя машины, IP сервера, COM-порт Arduino)
cd agents/rift-agent && npm i && npm run dev
cd dashboard && bun i && bun run dev
# Python-сервис зрения: pip install -r client/python-vision-service/requirements.txt
```

Для работы нужны клиент Lineage 2 в оконном режиме, Arduino с прошивкой HID на каждой машине и AutoHotkey.

В эту копию не вошли модели Tesseract (`rus/eng.traineddata`, скачиваются с github.com/tesseract-ocr/tessdata), отладочные датасеты скриншотов (~9 ГБ) и скомпилированный `activate.exe`: исходник лежит в `client/src/core/game-runner/ahk/`. Шаблоны настроек находятся в файлах `.env.example`.
